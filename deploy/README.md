# Деплой на VPS

Схема та же, что у остальных приложений на этом сервере: контейнер слушает
петлевой интерфейс, а TLS и маршрутизацию берёт на себя хостовый nginx.

```
   :443 ──▶ nginx (хост) ──▶ 127.0.0.1:3310 ──▶ контейнер devuz
                 │
                 ├──▶ 127.0.0.1:3300 ──▶ usta
                 └──▶ …остальные приложения
```

Свой reverse proxy внутри compose здесь поднимать нельзя: он попытался бы
занять порты 80 и 443 и уронил бы всё, что уже работает на этом VPS.

## Порядок

Полная пошаговая инструкция со всеми значениями — в корневом README, раздел
«Деплой». Кратко:

1. A-запись домена на IP сервера.
2. `git clone` в `/opt/devuz`, заполнить `.env`.
3. `docker compose up -d --build` — контейнер поднимается на `127.0.0.1:3310`.
4. Положить `deploy/nginx-devuz.conf` в nginx, получить сертификат certbot.
5. Поставить вебхук Telegram — только после того, как домен открывается по HTTPS.
6. Секреты в GitHub, чтобы дальше выкатывалось само.

## Файлы

| Файл | Что делает |
|---|---|
| `Dockerfile` | Двухстадийная сборка, standalone-вывод Next, непривилегированный пользователь |
| `docker-compose.yml` | Один сервис, привязан к петлевому интерфейсу |
| `deploy/nginx-devuz.conf` | Блок хостового nginx: HTTPS, кэш статики, потоковый ответ чата |
| `scripts/vps-deploy.sh` | Забирает ветку, пересобирает, ждёт healthcheck |
| `.github/workflows/deploy-vps.yml` | Проверка типов и сборки, затем выкатка по SSH |
| `.github/workflows/vps-doctor.yml` | Осмотр связи с сервером по кнопке — ничего не меняет |

## Две вещи, которые легко упустить

**`proxy_buffering off` в блоке nginx.** Ответ ассистента приходит потоком.
С буферизацией nginx копил бы его целиком и отдавал одним куском — вместо
печатающегося текста посетитель видел бы пустой экран несколько секунд и
уходил, решив, что чат не работает.

**`X-Forwarded-For`.** Лимитер частоты запросов берёт IP оттуда. Без этого
заголовка все посетители выглядели бы как один клиент с адресом `127.0.0.1`,
и первый же активный человек исчерпал бы лимит для всех остальных.

## «Отвалился коннект с гитхаб»

Цепочка состоит из трёх звеньев, и отказ каждого выглядит одинаково —
сайт показывает вчерашний коммит:

1. **Работа не дошла до `main`.** Ветка запушена, PR не открыт или не
   смержен. Выкатка при этом даже не запускалась: она живёт на push в
   `main`. Самый частый случай и единственный, который не чинится на
   сервере, — загляните в ветки репозитория раньше, чем в логи.
2. **Action не доехал до сервера.** Видно во вкладке Actions: красная
   «Выкатка на VPS». Сюда же относится мёртвый `VPS_SSH_KEY`.
3. **Сервер не забрал код.** Тот же красный Action, но падение внутри
   `vps-deploy.sh`, на первой строке — про доступ к репозиторию.

Что посмотреть, по порядку:

```bash
curl -s https://devuz.studio/api/health     # какой коммит реально крутится
```

Дальше — Actions → **«Осмотр связи с сервером»** → Run workflow. Он ничего
не меняет: показывает, чем сервер ходит за кодом, открыты ли чтение и
запись, отстал ли рабочий каталог, жив ли контейнер и фоновые службы,
осталось ли место на диске. Секретов в его выводе нет.

**Ключ для выкачки протухнуть не может.** Сервер забирает код по HTTPS из
публичного репозитория — ни ключа, ни токена для чтения не нужно. Если
`origin` всё же настроят на SSH и ключ однажды кончится, выкатка сама
перейдёт на HTTPS и напишет об этом в лог, а `origin` оставит как был:
право записи, если оно там есть, ей не принадлежит.

**Тревога о падении.** Задача `alarm` шлёт строку владельцу в Telegram тем
же каналом, что и ночные смены. Для этого нужен секрет репозитория
`SHIFT_REPORT_SECRET` — с тем же значением, что в `.env` на сервере
(Settings → Secrets and variables → Actions). Без него шаг молчит и пишет
об этом в лог: красный значок на странице, куда никто не заходит, — это
не уведомление.

## Проверка

```bash
curl -s https://devuz.studio/api/health
```

Отдаёт хеш выкаченного коммита и флаги настроенности — без значений самих
переменных. `telegram: false` на боевом сервере означает, что лиды сейчас не
доходят до продаж.
