# Откат

Написано для трёх часов ночи. Ничего не надо вспоминать и негде ошибиться —
команды выполняются сверху вниз.

Рельса две, и откатываются они по-разному: **код** выкатывается автоматически
на каждый push в `main`, **схема** применяется руками в SQL-редакторе Supabase.
Значит и сломаться они могут независимо, и чинить их надо раздельно.

---

## 1. Плохой деплой кода

Симптом: сайт не отвечает, отдаёт 500, или healthcheck красный.

```
cd /opt/devuz
docker compose ps
docker compose logs --tail=100 app
```

Откат на предыдущий образ. Docker хранит предыдущий слой, пока его не вычистили:

```
docker images | grep devuz
docker compose down
docker tag <ID предыдущего образа> devuz-app:latest
docker compose up -d
```

Если предыдущего образа не осталось — собрать из последнего рабочего коммита:

```
cd /opt/devuz
git log --oneline -10
git checkout <хеш рабочего коммита>
docker compose up -d --build
```

**После отката обязательно вернуть ветку:** `git checkout main`. Иначе
следующий автоматический деплой соберётся поверх detached HEAD и молча
выкатит не то, что вы ожидаете.

Проверка:

```
curl -s https://devuz.maximov-tech.ru/api/health
```

Ждём `{"ok":true,...}`. Поле `commit` показывает, какой код реально запущен.

## 2. Плохая миграция

Симптом: код выкатился, но эндпоинты падают на обращении к базе, либо в панели
висит красная плашка «миграция не применена».

**Каждая миграция едет с парным файлом отката.** Правило: `0004_staff.sql`
кладётся вместе с `0004_staff.down.sql`, и второй файл пишется в тот же момент,
что и первый, а не когда понадобится. Писать `down` под давлением — значит
писать его неправильно.

Порядок:

1. Открыть SQL-редактор проекта Supabase.
2. Выполнить содержимое `supabase/migrations/<номер>.down.sql`.
3. Откатить код на коммит **до** этой миграции (раздел 1).

Порядок обратный выкатке: там сначала SQL, потом код; здесь сначала код или
одновременно, но **никогда не откатывайте схему, оставив новый код работать** —
он обратится к колонке, которой уже нет.

### Если `down` не написан

Восстановление из копии (см. `deploy/backup-db.sh`):

```
ls -lt /var/backups/devuz/
gunzip -c /var/backups/devuz/devuz-<дата>.sql.gz | psql "$SUPABASE_DB_URL"
```

Это восстанавливает состояние на момент копии — то есть **теряет всё, что
пришло после неё**. Для лидов это значит потерянные заявки. Поэтому вариант
последний, и поэтому `down`-файлы пишутся сразу.

---

## 3. Проверка перед тем, как уйти спать

```
curl -s https://devuz.maximov-tech.ru/api/health
docker compose -f /opt/devuz/docker-compose.yml ps
systemctl status devuz-backup.timer
```

Здоровым считается: `ok:true`, контейнер `healthy`, таймер `active (waiting)`.

---

## 4. Чего делать нельзя

- **Не править схему в редакторе Supabase «на живую», чтобы починить прод.**
  Изменение, которого нет в `supabase/migrations/`, существует только в базе:
  следующий разработчик его не увидит, а следующая миграция об него сломается.
  Если правка срочная — она всё равно оформляется файлом миграции, просто
  сразу после.
- **Не откатывать схему вперёд** — то есть не «доправлять» неудачную миграцию
  ещё одной поверх, пока прод лежит. Сначала вернуть рабочее состояние, потом
  разбираться.
- **Не удалять образы `devuz-app`, пока новый не проверен.** Это единственный
  быстрый путь назад.
