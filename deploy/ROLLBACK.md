# Откат

Написано для трёх часов ночи. Ничего не надо вспоминать и негде ошибиться —
команды выполняются сверху вниз.

Рельса две, и откатываются они по-разному: **код** выкатывается автоматически
на каждый push в `main`, **схема** применяется руками в SQL-редакторе Supabase.
Значит и сломаться они могут независимо, и чинить их надо раздельно.

---

## 0. Выкатка применяет изменения самого скрипта только со следующего раза

Это уже не так — но знать стоит, потому что однажды стоило дорого.

GitHub Action запускает `/opt/devuz/scripts/vps-deploy.sh` — тот, что лежит на
сервере. Скрипт забирает новый код и раньше продолжал выполнять свою, уже
устаревшую логику: любая правка самого скрипта применялась только со следующей
выкатки. Понять это по логу было нельзя, он выглядел успешным.

Теперь скрипт после `git reset` передаёт управление свежей копии через `exec`.
Если когда-нибудь покажется, что выкатка «не видит» правку в самом скрипте, —
проверьте, что перезапуск на месте:

```
grep -n DEVUZ_DEPLOY_REEXEC /opt/devuz/scripts/vps-deploy.sh
```

Запустить выкатку руками, не дожидаясь push:

```
bash /opt/devuz/scripts/vps-deploy.sh
```

## 1. Плохой деплой кода

Симптом: сайт не отвечает, отдаёт 500, или healthcheck красный.

```
cd /opt/devuz
docker compose ps
docker compose logs --tail=100 app
```

Откат на предыдущий образ. Docker хранит предыдущий слой, пока его не вычистили:

```
docker images | grep devuz
docker compose down
docker tag <ID предыдущего образа> devuz-app:latest
docker compose up -d
```

Если предыдущего образа не осталось — собрать из последнего рабочего коммита:

```
cd /opt/devuz
git log --oneline -10
git checkout <хеш рабочего коммита>
docker compose up -d --build
```

**После отката обязательно вернуть ветку:** `git checkout main`. Иначе
следующий автоматический деплой соберётся поверх detached HEAD и молча
выкатит не то, что вы ожидаете.

Проверка:

```
curl -s https://devuz.maximov-tech.ru/api/health
```

Ждём `{"ok":true,...}`. Поле `commit` показывает, какой код реально запущен.

## 2. Плохая миграция

Симптом: код выкатился, но эндпоинты падают на обращении к базе, либо в панели
висит красная плашка «миграция не применена».

**Каждая миграция едет с парным файлом отката.** Правило: `0004_staff.sql`
кладётся вместе с `0004_staff.down.sql`, и второй файл пишется в тот же момент,
что и первый, а не когда понадобится. Писать `down` под давлением — значит
писать его неправильно.

Порядок:

1. Открыть SQL-редактор проекта Supabase.
2. Выполнить содержимое `supabase/migrations/<номер>.down.sql`.
3. Откатить код на коммит **до** этой миграции (раздел 1).

Порядок обратный выкатке: там сначала SQL, потом код; здесь сначала код или
одновременно, но **никогда не откатывайте схему, оставив новый код работать** —
он обратится к колонке, которой уже нет.

### Откатывать только с конца

Миграции связаны внешними ключами, и цепочка идёт в одну сторону:

| Миграция | На что опирается |
|---|---|
| `0004_staff` | — |
| `0005_lead_ownership` | `staff`, `leads` |
| `0006_lead_messages` | `staff`, `leads` |
| `0007_projects` | `staff`, `leads` |
| `0008_orders` | `staff` |
| `0009_scout_signals` | `staff`, `leads` |

Откат `0004` при существующих `0005`–`0009` **не пройдёт**: Postgres не даст
удалить `staff`, пока на неё ссылаются. Откатывайте с самого большого номера
вниз до нужного — и ровно до нужного, не дальше.

Проверить, что на самом деле применено:

```
select tablename from pg_tables where schemaname = 'public' order by tablename;
```

Ожидаемый полный набор: `audit_events`, `lead_messages`, `lead_reminders`,
`leads`, `login_tokens`, `orders`, `projects`, `scout_signals`, `staff`,
`staff_sessions`.

### Версия pg_dump

Копия снимается только клиентом не старше сервера. Ubuntu 22.04 ставит
`postgresql-client` версии 14, Supabase крутит 17 — то есть после обычного
`apt install postgresql-client` бэкапы не делаются вовсе, а таймер при этом
отрабатывает каждую ночь и выглядит живым.

`backup-db.sh` проверяет это сам и, если на машине есть docker, берёт pg_dump
нужной версии из образа `postgres:<мажор>` — возиться с чужим apt-репозиторием
не нужно. Без docker он печатает команды установки. Проверить руками:

```
pg_dump --version
psql "$(grep -m1 '^SUPABASE_DB_URL=' /opt/devuz/.env | cut -d= -f2-)" -tAc 'show server_version'
```

Первое число у клиента должно быть не меньше, чем у сервера.

### Если `down` не написан

Восстановление из копии (см. `deploy/backup-db.sh`):

```
ls -lt /var/backups/devuz/
gunzip -c /var/backups/devuz/devuz-<дата>.sql.gz | psql "$SUPABASE_DB_URL"
```

Это восстанавливает состояние на момент копии — то есть **теряет всё, что
пришло после неё**. Для лидов это значит потерянные заявки. Поэтому вариант
последний, и поэтому `down`-файлы пишутся сразу.

## 3. Проверка перед тем, как уйти спать

```
curl -s https://devuz.maximov-tech.ru/api/health
docker compose -f /opt/devuz/docker-compose.yml ps
systemctl list-timers devuz-backup.timer devuz-reminders.timer
```

Здоровым считается: `ok:true`, контейнер `healthy`, **оба** таймера в списке с
непустым `NEXT`.

Таймера нет в списке — значит соответствующей переменной нет в `/opt/devuz/.env`,
и выкатка намеренно его не включила:

```
grep -c '^SUPABASE_DB_URL=.\+' /opt/devuz/.env       # бэкапы
grep -c '^REMINDER_SWEEP_SECRET=.\+' /opt/devuz/.env # напоминания
```

Ноль означает не поломку, а незаданную переменную. Это сделано нарочно: таймер,
получающий 403 каждые пять минут, создаёт видимость работающей рассылки.

Один инвариант, который стоит проверять после любой правки схемы, — доступ:

```
select tablename, rowsecurity,
       (select count(*) from pg_policies p
        where p.schemaname = t.schemaname and p.tablename = t.tablename) as policies
from pg_tables t where schemaname = 'public' order by tablename;
```

У **всех** строк должно быть `rowsecurity = true` и `policies = 0`. Появившаяся
политика или выключенный RLS означают, что таблица открылась анонимному ключу —
тому самому, который лежит в браузере у любого посетителя.

## 4. Журнал откатить нельзя

`audit_events` защищена триггером: `update` и `delete` по ней бросают исключение,
и снять триггер `service_role` не может — таблица принадлежит `postgres`.

Это не поломка и не то, что нужно чинить в три часа ночи. Если строки в журнале
мешают — значит кто-то пытается убрать след, и правильный ответ здесь «нет».
Единственный законный способ убрать эти строки — откат `0004_staff.down.sql`,
то есть удаление журнала целиком вместе с сотрудниками и сессиями.

## 5. Никто не может войти в панель

Симптом: `/login` боту отвечает как незнакомцу, в панель не пускает никого.

Причина почти всегда одна: в `staff` нет активной строки с вашим Telegram-id.
Так бывает после восстановления из копии, сделанной до заведения сотрудников.

Проверить и починить (id берётся из `TELEGRAM_SALES_CHAT_ID`, если бот пишет
брифы в личку):

```
select telegram_user_id, display_name, role, is_active from public.staff;
```

```
insert into public.staff (telegram_user_id, display_name, role)
values (<ваш telegram id>, '<имя>', 'admin')
on conflict (telegram_user_id) do update
  set role = 'admin', is_active = true;
```

Забытая деталь: восстановление из копии возвращает и `staff_sessions`. Старые
куки снова начинают работать. Если копию восстанавливали после утечки — почистите:

```
delete from public.staff_sessions;
```

## 6. Чего делать нельзя

- **Не править схему в редакторе Supabase «на живую», чтобы починить прод.**
  Изменение, которого нет в `supabase/migrations/`, существует только в базе:
  следующий разработчик его не увидит, а следующая миграция об него сломается.
  Если правка срочная — она всё равно оформляется файлом миграции, просто
  сразу после.
- **Не откатывать схему вперёд** — то есть не «доправлять» неудачную миграцию
  ещё одной поверх, пока прод лежит. Сначала вернуть рабочее состояние, потом
  разбираться.
- **Не удалять образы `devuz-app`, пока новый не проверен.** Это единственный
  быстрый путь назад.
