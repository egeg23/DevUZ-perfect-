# 1. База ОС: на чём строим

Задача: выбрать основу, на которой мы вдвоём (владелец и сессии Claude)
соберём свою систему для коробки. Система неизменяемая (её нельзя поменять
изнутри), обновляется целиком с откатом, грузится только с нашей подписью,
работает на AMD Strix Halo (Лайт, Про) и на NVIDIA RTX PRO 6000 (Джарвис,
Джарвис Max) и называется нашим именем.

Обозначения: **[проверено]** — сверено с источником при подготовке плана,
02.11.2026; **[не проверено]** — по памяти или по одному источнику, сверить
до работы.

## Что важно в выборе

| Критерий | Почему важен для нас |
|---|---|
| Железо AMD Strix Halo | Лайт и Про. Нужно ядро не старше 6.18.4, драйвер amdgpu, Vulkan (Mesa RADV), по возможности ROCm для gfx1151 |
| Железо NVIDIA Blackwell | Джарвис. RTX PRO 6000 работает только с **открытыми** модулями ядра NVIDIA; нужна CUDA и право класть драйвер в наш образ |
| Неизменяемость и A/B | Обновление целиком, неудачное откатывается само: в офисе клиента нет админа |
| Secure Boot своими ключами и TPM | Мягкая защита (раздел 4): грузится только наше, диск открывается сам только на «своей» коробке |
| Бренд | Систему называем своим именем. Ubuntu и Fedora не дают называть изменённую систему их именем, а Ubuntu ещё и требует вычистить свой бренд |
| Объём работы | Инженеров нет. Чем больше готового и чем проще устройство, тем лучше: Claude хорошо пишет конфиги и скрипты, но отлаживать загрузчик на железе придётся владельцу руками |
| Зрелость | Продаём бизнесу: экспериментальные части в основе нельзя |

## Варианты

### A. Debian 13 + свой образ (mkosi, UKI, dm-verity, systemd-sysupdate)

Свой образ из пакетов Debian собирается программой mkosi (проект systemd).
Образ: раздел `/usr` только для чтения (erofs) с подписанной проверкой
dm-verity, загрузчик systemd-boot и «единый образ ядра» (UKI: ядро,
initrd и строка запуска одним подписанным файлом), обновления
`systemd-sysupdate` по схеме A/B со счётом загрузок и откатом, разметка
диска `systemd-repart`, шифрование диска `systemd-cryptenroll` с ключом в
TPM по подписанной политике. Это ровно схема «Fitting Everything Together»
от авторов systemd, и у неё есть готовый живой образец — **ParticleOS**:
mkosi, erofs с подписанным dm-verity для `/usr`, подписанные UKI и ESP,
`systemd-sysupdate` с A/B и откатом, установщик через `systemd-repart`,
рецепты для Debian, Fedora, Arch и SUSE, собирается и подписывается
своими ключами **[проверено: github.com/systemd/particleos, доклад FOSDEM
2026]**.

- **AMD**: в Debian 13 ядро 6.12 (на весь срок выпуска), но в
  `trixie-backports` идёт свежее ядро: весной 2026 — ветка 6.18 (6.18.5 → 6.18.15), на 02.11.2026 — уже 7.2.11 (в backports живёт только последняя версия, старые удаляются) с
  исправлениями amdgpu **[проверено: tracker.debian.org]**. Для Strix Halo
  сообщество называет нижней планкой 6.18.4 **[проверено, один источник:
  community.frame.work, январь 2026]**. Vulkan — Mesa из backports.
  ROCm: AMD выпускает пакеты для Ubuntu, RHEL и SLES, не для Debian;
  поддержка gfx1151 в ROCm 7.x по источникам расходится (одни пишут
  «официально с 7.2», другие — «полностью с 7.2.2») **[не проверено,
  источники спорят]**. Поэтому ROCm в коробке — в контейнере, а основной
  путь моделей на AMD — Vulkan (llama.cpp), который от ROCm не зависит.
- **NVIDIA**: открытые модули ядра NVIDIA (`open-gpu-kernel-modules`,
  MIT/GPLv2) собираем при сборке образа под наше ядро и подписываем нашим
  ключом модулей. RTX PRO 6000 без открытых модулей не работает **[проверено:
  Red Hat KB 7138923, форум NVIDIA]**. Пользовательскую часть драйвера и
  CUDA NVIDIA разрешает распространять «без изменений в двоичных файлах»
  (исключение для Linux в лицензии драйвера; библиотеки CUDA — по списку
  «Attachment A» в EULA CUDA) **[частично проверено: текст старых EULA
  CUDA; текущий текст лицензии драйвера R580+ прочитать перед первой
  продажей]**. NVIDIA держит свой репозиторий CUDA для Debian
  **[не проверено для Debian 13]**.
- **Бренд**: Debian разрешает производные системы своим именем, нельзя
  только выдавать их за Debian («основано на Debian» — можно) **[не
  проверено дословно: debian.org/trademark]**.
- **Объём работы**: средний. Всё — файлы настроек mkosi и юниты systemd,
  то есть текст, который Claude пишет хорошо. Образ проверяется в QEMU с
  OVMF (Secure Boot) и swtpm (программный TPM) без железа: загрузка,
  подпись, TPM, A/B, откат — всё до прихода коробки.
- **Зрелость**: Debian — одна из самых старых и спокойных систем, обновления
  безопасности приходят годами. Связка mkosi + sysupdate моложе, но её
  ведёт сам systemd, на ней стоят ParticleOS и GNOME OS.
- **Минусы**: свежего ядра и Mesa в основном Debian нет — живём на
  backports; ROCm не родной; свой конвейер сборки — наш, его надо держать.

### B. Fedora bootc / Atomic (образ системы как контейнер)

Система собирается как контейнерный образ (`Containerfile`), обновляется
`bootc upgrade` с откатом. Свежее ядро и Mesa из коробки, NVIDIA через
akmods и RPM Fusion или готовые образы Universal Blue.

- «Запечатанные» образы (systemd-boot + UKI + composefs с fs-verity,
  своими ключами Secure Boot) в апреле 2026 вышли только **тестовыми**, а
  бэкенд composefs в bootc помечен «экспериментальный, не для боевой
  работы» **[проверено: Fedora Magazine, документация bootc]**. Без
  печати — обычная загрузка с ostree, это слабее, чем dm-verity.
- Бренд: имя Fedora в изменённой системе нельзя, «remix» — с условиями.
- Короткая жизнь выпуска (≈13 месяцев) — для коробки, которая стоит у
  клиента годами, это лишние большие переезды.
- **Вывод**: хороший запасной путь через год, когда запечатанные образы
  станут боевыми. Сейчас для продажи сыро.

### C. Kairos (неизменяемая система для «края» сети, CNCF)

Собирает загрузочные образы из контейнеров, есть режим Trusted Boot:
UKI, подпись своими ключами, шифрование данных по политике PCR, обновления
A/B **[проверено: kairos.io/docs/installation/trustedboot]**.

- Близко к нужному «из коробки». Но заточен под кластеры Kubernetes (k3s),
  своё устройство (AuroraBoot, свои агенты), примеры Trusted Boot — на
  Ubuntu и своей базе Hadron, про Debian документации не нашлось
  **[проверено: поиск по kairos.io]**. Потеря ключей подписи — нельзя
  выпускать обновления (так у всех).
- **Вывод**: запасной путь, если свой mkosi-образ не пойдёт. Минус — чужой
  слой, который придётся понимать целиком, и Ubuntu внутри (бренд).

### D. NixOS

Вся система описывается одним текстом, откат к любому прошлому состоянию,
Secure Boot через lanzaboote.

- Мощно, но язык Nix сложен, а неизменяемость там «по договорённости»
  (`/nix/store` можно поменять с root), dm-verity для всей системы —
  нестандартный путь. Драйверы NVIDIA — хорошо, ROCm — с оговорками.
- **Вывод**: для нас лишняя сложность без выигрыша в защите.

### E. openSUSE MicroOS / SLE Micro

Снимки btrfs и «транзакционные» обновления с откатом.

- Откат есть, но нет проверки подписи всей системы (dm-verity), Secure Boot
  своими ключами — руками. Бренд openSUSE в изменённой системе нельзя.
- **Вывод**: не даёт главного — запертой системы.

### F. Подходы «как ChromeOS» (ChromiumOS, ChromeOS Flex)

У ChromeOS ровно наша модель защиты (A/B, dm-verity, проверенная
загрузка), но ChromiumOS — огромная сборка Gentoo с инструментами Google,
поднимать её под своё железо вдвоём нереально, а Flex — продукт Google.
**Вывод**: берём идею, не код.

### G. Talos Linux, Flatcar, Bottlerocket

Неизменяемые системы для серверов с контейнерами. Talos — только
Kubernetes и API, без своих служб на хосте; Flatcar и Bottlerocket —
узлы облаков. NVIDIA там есть, Strix Halo и звук/USB для спикерфона —
не их задача. **Вывод**: не под коробку в офисе.

## Рекомендация

**Debian 13 «trixie» + свой образ на mkosi по схеме ParticleOS**:
systemd-boot и UKI, `/usr` на erofs с подписанным dm-verity, A/B через
`systemd-sysupdate`, данные на LUKS2 с ключом в TPM по подписанной политике
PCR, ядро из `trixie-backports` (сейчас 7.2, не ниже 6.18.4; или наша сборка долгой ветки из исходников
Debian той же ветки), NVIDIA — открытые модули, собранные и подписанные при
сборке, и отдельное расширение системы (`systemd-sysext`) с драйвером и
CUDA только в образах Джарвиса.

Почему:

1. Это единственный вариант, где **всё нужное уже боевое**: dm-verity,
   UKI, sysupdate, TPM — части systemd, а не эксперимент.
2. **Всё проверяется без железа** — в QEMU с OVMF и swtpm, и даже в GitHub
   Actions. Первые 6–8 недель работы не ждут коробку.
3. **Бренд чистый**: своя система «на основе Debian».
4. **Debian живёт долго** (≈5 лет с LTS): коробка не переезжает на новую
   основу каждый год. Переход на Debian 14 (ожидается в 2027) — плановый,
   одним большим обновлением.
5. **Для двоих посильно**: всё — текстовые файлы и юниты; Claude пишет их,
   владелец проверяет на железе.

Запасной путь — Kairos (если наш образ упрётся в загрузку на железе) и
Fedora bootc с печатью, когда она станет боевой (смотреть летом 2027).

## Что держим в уме

- **Ядро.** Debian меняет ядро в backports без нашего спроса. Мы
  закрепляем версию в образе и поднимаем её сами после прогона тестов
  (на QEMU и на образце). Закрепить версию внутри backports нельзя — использованные `.deb` храним у себя (GitHub Release), а до недели 5 решаем: идти за backports или собирать своё ядро на долгой ветке (см. [week-01.md](week-01.md)).
- **Mesa.** Для скорости Vulkan на Strix Halo нужна свежая Mesa — из
  backports или своя сборка пакета. Проверить на образце.
- **ROCm.** В коробке — контейнер с ROCm от AMD или из сборок TheRock;
  нужен для Whisper на GPU, картинок (ComfyUI с PyTorch) на AMD. Основной
  чат на AMD от ROCm не зависит (Vulkan).
- **NVIDIA и ядро.** Каждое новое ядро — пересборка открытых модулей и
  повторная подпись. Это делает конвейер, руками ничего.
