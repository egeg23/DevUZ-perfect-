# Неделя 1: первый образ DevUz OS грузится в виртуалке

Старт — 02.11.2026, слово владельца: «Ну погнали в новой сессии тогда —
неделя 1!». Общий план — [06-roadmap.md](06-roadmap.md), часть А.

## Цель недели

Образ системы на Debian 13 собирается в GitHub Actions на каждый пуш и
загружается в QEMU до готовности. Проверку делает тест в Actions, а не
человек. Разметка диска сразу заложена под A/B, чтобы неделя 2 не
переделывала неделю 1.

Не в этой неделе: dm-verity с подписью, обновления A/B, Secure Boot,
TPM (недели 2–3), приложения и модели (недели 4–6).

## Где

- Репозиторий `egeg23/devuz-os`, **открытый** (решение — README, «Решения
  владельца»). Создаёт владелец (у сессий нет права создавать
  репозитории), пустым, без README.
- Ключей там нет никогда: ни тестовых закрытых (они создаются на лету в
  Actions и выбрасываются), ни боевых.
- Правила репозитория — свой `CLAUDE.md`: русский язык в документах, PR и
  слияние squash, как только сборка зелёная (как в этом репозитории),
  никаких цен поставщиков, ключей и данных клиентов.

## Задачи

| № | Что | Готово, когда |
|---|---|---|
| 1 | Каркас: `README.md` (что это, как собрать), `CLAUDE.md`, лицензия рецептов (Apache-2.0), `.gitignore` (`mkosi.key`, `mkosi.crt`, `*.key`, `out/`, `mkosi.output/`) | файлы в main |
| 2 | Рецепт mkosi: `Distribution=debian`, `Release=trixie`, репозиторий `trixie-backports` включён; ядро — `linux-image-amd64` из backports, версия закреплена; systemd-boot + UKI (`Bootable=yes`, `UnifiedKernelImages=yes`), `Format=disk`; минимальный набор пакетов; без пароля root | `mkosi build` проходит локально в сессии |
| 3 | Версия mkosi закреплена (тег из git-репозитория mkosi, ставится через `pipx`/`pip` из git) — Debian 13 и Ubuntu 24.04 возят старые версии | в README и в Actions одна и та же версия |
| 4 | `os-release`: `NAME="DevUz OS"`, `ID=devuz`, `ID_LIKE=debian`, `VERSION_ID` и `IMAGE_VERSION` из даты и хеша коммита | тест читает их внутри загруженной системы |

| 6 | Два профиля: `prod` — без getty на консолях, без SSH; `dev` — консоль на последовательном порту для тестов. Тест гоняет `dev`, но проверяет, что в `prod` getty и sshd не включены | тест по манифесту `prod` |
| 7 | Служба `devuz-ready.service` после `multi-user.target`: пишет в последовательный порт строку `DEVUZ-READY <IMAGE_VERSION>`. Экран «Состояние» на tty1 — текстом: версия, адрес, `http://devuz.local` (QR — позже) | строка ловится тестом |
| 8 | GitHub Actions `build.yml`: сборка на `ubuntu-24.04`, кэш пакетов, артефакт — образ (сжатый) и манифест пакетов; запуск на пуш и PR | зелёная галочка на PR |

## Проверка в конце недели (для владельца)

1. Открыть Actions в `devuz-os`: последняя сборка main зелёная.
2. В журнале теста — строка `DEVUZ-READY 2026.11.xx-<хеш>` и версии ядра
   и systemd.
3. Скачать артефакт — образ можно запустить у себя в QEMU/VirtualBox
   (инструкция в README) и увидеть экран «Состояние» с надписью DevUz OS.

## Риски недели и что делаем

| Риск | Что делаем |
|---|---|
| Новый mkosi нужен с ветки main (так у ParticleOS) | закрепляем последний тег; если чего-то нет — коммит main, записанный в README |
| Ядро 6.18 из backports называется по-другому или уже сменилось на новее | закрепляем точную версию пакета; проверка в тесте |
| В GitHub Actions нет `/dev/kvm` | TCG, таймаут 15 минут; если медленно — включаем KVM по документации GitHub для Linux-раннеров |
| Мало места на раннере | образ без моделей и без NVIDIA — до 2–3 ГБ; чистка раннера перед сборкой |
| Сборка в контейнере сессии не идёт (нет loop-устройств, нет прав) | собирать и проверять в Actions, в сессии — только правка рецептов |
